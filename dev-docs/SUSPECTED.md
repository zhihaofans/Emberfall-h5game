## 1. `lastSeen` 被 32 位截断 → 每次载入白拿 8 小时离线收益

- **位置**：`survival.html` · `normalizeState` 的 `g.lastSeen = g.lastSeen|0 || now`；`loadSave` 的 `const rawTs=(data.g&&data.g.lastSeen)|0`
- **现象**：`Date.now()` 是 13 位（如 `1700000000000`），`|0` 会截成 32 位有符号整数 `-807049216`。于是 `Date.now() - 负数` 得到天文数字，`settleOffline` 直接吃满 8 小时封顶。
- **影响**：**每次打开游戏都白拿一次 8 小时离线产出**（食物/净水/木材），且存档里的 `lastSeen` 会被写成负数。老玩家几乎每局都在享受这个"福利"。
- **建议**：改用数值判断，不做 32 位截断：
  `const ts = Number(g.lastSeen); g.lastSeen = Number.isFinite(ts) && ts > 0 ? ts : now;`
- **影响面**：修好后离线收益会"变少"（其实是回归正常），玩家可能有感。
- **状态**：✅ **已生效（3.0.0 起）**：`src/core/save.mjs` 已修并有测试，新架构 3.0.x 线上运行的就是修好的版本。

## 2. `newGame()` 漏写 `__v1274_comp` → 新玩家白拿补偿

- **位置**：`survival.html` · `newGame()` 只写了 `__v1171_comp: 1`
- **现象**：`normalizeState` 里 v1.27.4 的一次性补偿判断是"没有标记就补"，而新档从来没写这个标记。
- **影响**：**每个新玩家第一次读档白拿 🪬不死图腾 ×1 + 🎰抽奖券 ×2**。本意是补偿 v1.27.4 之前金币变 NaN 的受害玩家。
- **建议**：`newGame()` 里补上 `__v1274_comp: 1`（与 `__v1171_comp` 同样处理）。这正是 `AGENT.md` §7 历史坑 #5 描述的那类错误。
- **影响面**：新玩家少拿 1 图腾 + 2 抽奖券；老档不受影响。
- **状态**：✅ **已生效（3.0.0 起）**：`createNewState` 写入 `__v1274_comp`，新玩家不再白拿补偿。

## 3. 非冬季天气跳过「暴雨」，夏天会下「暴风雪」

- **位置**：`survival.html` · `nextDay()` 的天气分布
  ```js
  if (G.season===3) G.weather = r<.45?0: r<.7?1 : r<.85?2 : r<.95?3:4;  // 冬：0/1/2/3/4
  else              G.weather = r<.5?0 : r<.75?1 : r<.9?2 : 4;           // 其它季：0/1/2/4
  ```
- **现象**：春夏秋三季**永远不会出现 3（暴雨）**，但有 10% 概率直接跳到 4（暴风雪）。
- **影响**：
  - 语义上"夏天暴风雪"很怪；
  - 数值上 4 比 3 更狠：每日水分消耗 28 vs 20、温室系数 0.3 vs 0.55、捕兽夹 0.7 vs 0.55、太阳能 0 vs 0.15。等于**春夏秋多了一种比暴雨更严重的灾害天气**。
- **建议**：非冬季那一支的 `4` 改成 `3`（暴雨）。改完之后"暴风雪"只在冬季出现。
- **影响面**：中。会改变春夏秋的生存压力与设施产出期望；对已在玩的存档无兼容问题（只是天气索引）。
- **状态**：✅ **已修正（3.0.11）**：非冬季分布改为 `0/1/2/3`（暴雨），暴风雪只在冬季；单测断言改为「非冬季有 3、没有 4」。

## 4. 资源「不可出售」有两种写法

- **位置**：`survival.html` · `RES_PRICE`
- **现象**：`expPotion:0` / `luckyDraw:0` / `lifePotion:0` 是"有键但价格 0"；`totem` / `adrenaline` 是"压根没有键"。渲染层 `if (!RES_PRICE[k]) return;` 对两者效果相同（都不显示出售按钮）。
- **影响**：语义混乱，容易误以为"价格 0 表示能卖 0 块"，也让"新增资源要改几处"的清单变得不可预测。
- **建议**：统一为「缺项 = 不可出售」，价格 0 的三项直接从表里去掉。
- **影响面**：无（行为一致）。
- **状态**：✅ **已生效（3.0.0 起）**：新口径为 `price: null` = 不可出售，`resPrices()` 不含它；旧文件的 5 处只作为对拍基准。

## 5. `stats.days` 有两个默认值

- **位置**：`newGame()` 里 `stats.days: 0`；`normalizeState` 的 `def.stats.days: 1`
- **现象**：同一字段，新档是 0，补字段的老档是 1。
- **影响**：低。只影响"累计天数"的展示与个别统计，不影响判定。
- **建议**：统一为 0（新档语义），或在注释里明确两者差异（当前已在 `core/save.mjs` 注释说明）。
- **状态**：✅ **已关闭（3.0.0 起统一为 1）**：`createNewState` 与 `normalizeState` 都用 `stats.days: 1`，代码里已加注释说明。

## 6. 强化「Lv.10 起额外消耗」的措辞与实际触发点不一致

- **位置**：`survival.html` · `upgradeCost`：`if (lv>=10) { cost.rune = lv-9; ... }`
- **现象**：`lv` 是"当前等级"，`lv>=10` 表示**从 10 级升到 11 级**这一步才开始加符石/合金；而注释与文档写的是"11–15 级需要"，玩家读起来像"10 级就要"。
- **影响**：纯文案/理解问题，数值本身没问题。
- **建议**：文案统一成"升到 11 级起额外消耗"。
- **状态**：✅ **已修正文案（3.0.11）**：注释、面板、AGENT 统一成「升到 11 级起额外消耗」。

## 7. 击杀 Boss 时抛异常 → 奖励与成就全部不发

- **位置**：`survival.html` · `fight()` 第 4339 行 `const b=combat.b; combat=null;`，第 4359 行又读 `combat.isPharaoh`
- **现象**：`combat` 已被置为 `null`，再读 `.isPharaoh` 直接 `TypeError`。**只有"打死 Boss"这条路径会走到**，普通怪击杀不受影响（普通分支不读 `combat`）。
- **影响**：
  - 击杀兽王 / 法老时，`stats.bossKills` / `pharaohKills` 不增加、奖励不发、成就（boss / boss2 / boss3 / pharaoh1-3）不触发；
  - 异常也会中断 `renderAll()` / `save()` / `checkDeath()`，界面停在战斗弹窗状态；
  - 因为 Boss 战本身很难（要钢刀/铁甲 + 高等级），实际很少被触发，所以一直没被发现。
- **复现**：`tests/unit/combat-fight.test.mjs` 里 `assert.throws(() => env.__fight('fight'), /isPharaoh/)`。
- **建议**：把 `const isPharaoh = combat.isPharaoh;` 提到 `combat = null` 之前（一行修复）。
- **影响面**：修好后 Boss 首杀才真正可完成（成就、奖励、Boss 三阶段成长链全部解锁）。属于**行为修复**，会让「兽王/法老」从"打不死"变成"打得死"。
- **状态**：✅ **已生效（3.0.0 起）**：`src/core/combat.mjs` 用参数传 `isPharaoh`，Boss 击杀会正常发奖励、加计数、触发成就。

## 8. 进度总览：强化分母写死 10，实际上限 15

- **位置**：`survival.html` · `openProgress()`：`const maxUp=upKeys.length*10`，标签写 `${totalUp}/${maxUp}`、每项 `/10`
- **现象**：`UPGRADES` 里 4 项都是 `max: 15`，真实上限是 60；面板却按 40 算，玩家强到 15 级会显示 `45/40` 之类的越界值，进度条也永远到不了"满"。
- **影响**：纯展示（不写入存档、不影响数值），但会让人误判强化是否已练满。
- **建议**：分母按 `UPGRADES[k].max` 求和。
- **状态**：**已修正**（2026-10-27，`core/progress.mjs` 的 `upgradeProgress()`；测试锁 4×15=60）。
